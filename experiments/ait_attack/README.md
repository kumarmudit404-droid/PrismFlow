## 3. What epsilon 1.0 is worth, per view and per direction

`attack.epsilon_rescaled` is **false** in `config.yaml`: Part 09's grid (0.2, 0.5, 1.0, 2.0) is carried over unrescaled against features whose per-view std is measured below. A fixed epsilon is therefore a DIFFERENT relative perturbation in each view. `epsilon 1.0 in std units` is `1.0 / std`, so a larger number means the same epsilon moves that view further relative to its own spread.

The last column is a DIFFERENT quantity and must not be read as attack strength: it is the fraction of that view's NATIVE feature cells the attack actually moves when that view is compromised alone (`chorus_eps1.0`, k=1, seed 0, from `padding_audit.json`). A cell is left untouched where the objective's gradient is exactly zero, since the step is `epsilon * sign(gradient)`. The denominator is every native cell in the test set, so windows in which the view is absent are inside it. One seed, structural, NOT a 5-seed finding.

## 4. Padding columns: the attack does NOT write into them

**The Part 29 post-run brief asked this README to state that the frozen chorus attack also writes +/- epsilon into the structurally-zero padding columns. That premise is not what this pipeline does, and the measurement below is why.**

AIT views are 8-10 features wide and the tensor is padded to 10 columns, so every view but `suricata` carries columns that are structurally zero in the data. Those columns ARE inside the attack's mask: `chorus_attack` steps `step_size * gradient.sign() * mask` where `mask` covers all 10 columns of a compromised view (`prismflow/attacks/chorus.py:148-149`, `prismflow/attacks/chorus.py:165-166`). They are nonetheless never moved.

**Measured answer: NO. Across both directions, all five views, chorus and pgd, at epsilon 1.0 and 2.0, every padding cell's delta is exactly zero and the objective's gradient with respect to every padding column is exactly zero. The padding columns lie inside the attack's mask but are unreachable through the encoder, so the brief's premise that the attack writes +/- epsilon into them is NOT what this pipeline does.**

The mechanism is `experiments/ait_clean/run_ait_clean.py:300-301`: view_configs gives each view's encoder its native input width, so the padded columns are never read; the gradient with respect to them is identically zero and sign(0) == 0.

## 8. Not like-for-like with Part 10's clone_k2

**Confirmed from the code, not inferred.** Part 10's `clone_k2` compares a 6-view attacked model against a 4-view clean reference:

- `experiments/comparison/run_comparison.py:88` declares `clone_k2` as `{kind: clone, k: 2}`, and `:69` sets `n_views: 4`.
- `prismflow/data/corruption.py:15-20` - `duplicate_view` APPENDS k copies of a view, so the clone condition runs 4 + 2 = 6 views.
- `experiments/comparison/run_comparison.py:232-234` and `:271` build and select a model of width `4 + k` for a clone condition.
- `:279-281` take the reference scores from the `clean` condition, which is `k = 0` and therefore width 4; `:292` is `roc_auc(scores, reference)`.

So the two score vectors come from models of different width. That matters because the suspicion score is a MAXIMUM, not a mean: `prismflow/statistics/suspicion.py:43-45` and `:253` take `masked.max(axis=(1, 2))` over the off-diagonal pairs selected at `:248-249` by `~np.eye(n_views)`. A 6-view model maximises over **30** off-diagonal entries and the 4-view clean reference over **12**. A maximum over 30 draws is stochastically larger than a maximum over 12 even when every per-pair distribution is identical, so part of clone_k2's AUC 0.8743 +/- 0.0583 is the width change itself rather than detected duplication.

Part 29 has no such asymmetry: every condition and its clean reference run the same 5-view model, so the AUCs in section 7 are attacked-vs-clean at fixed width. **Any comparison between the two Parts is therefore qualitative only, and the numbers must not be differenced.** Part 29 also runs on real AIT logs with 5 views and a label one view solves, against Part 10's 4-view synthetic data.

### L5 - the detector inherits the dependence blind spot and inverts under missing evidence

- **A_rm_to_santos:** 129 of 187 conditions below AUC 0.5; range 0.2384..0.7133. Missingness: `missing_30` 0.3169, `missing_50` 0.2384.
  - dns COMPROMISED: 0.3139..0.6051 over the headline grid points.
  - dns NOT compromised: 0.4166..0.6601 over the headline grid points.
- **B_santos_to_rm:** 159 of 187 conditions below AUC 0.5; range 0.1314..0.6220. Missingness: `missing_30` 0.3166, `missing_50` 0.2059.
  - dns COMPROMISED: 0.1842..0.6220 over the headline grid points.
  - dns NOT compromised: 0.1970..0.4810 over the headline grid points.

**Verdict: L5 is reproduced and is WORSE than L5 states, on both sides of the dns split.** L5 describes a detector that degrades to chance and inverts under missingness. On AIT the majority of all conditions - attacked, not merely missing - sit below chance, so the flag fires LESS under attack than under clean operation across most of the grid. Section 7.1 rules out the saturated-detector explanation on the subset measured: scores are well spread. The inversion is directional.

**What this protocol does and does not put to the test.** The numbers above are a property of THIS measurement design, not of a deployed detector, and three design choices decide them:

- **Every window in the evaluated batch is attacked.** `attack: batch_size` is 1200 against A_rm_to_santos n_test=1108, B_santos_to_rm n_test=1145, so each direction is one batch and `views = views + result.delta` (`run_ait_attack.py:511`) perturbs all of it. There is no clean population inside an attacked run.
- **The baseline is the same windows unattacked.** `detector_auc(cell['_scores'], clean_scores)` (`run_ait_attack.py:920`) scores the fully-attacked run against the clean pass over the same test windows for that direction/system/seed, and the one clean reference is reused by every subset in that unit. The AUC is therefore a between-run comparison, not a within-batch one.
- **Partially contaminated batches were NOT tested.** No cell mixes attacked and clean windows, and no cell varies the contaminated fraction; that axis is absent from the grid, so this Part reports not measured for it.

A deployed detector sees a mostly-clean stream and must flag a small contaminated part of it. That is the regime this Part does not enter. The below-chance AUCs above are a real and reproducible property of the all-or-nothing protocol, and they do not license a claim about detection rates in deployment in either direction.

### L8 - detection and correction fail together

- **A_rm_to_santos, dns COMPROMISED:** across 85 conditions, Pearson r between per-cell detector AUC and mean dependence = **-0.4334**.
- **A_rm_to_santos, dns NOT compromised:** across 100 conditions, Pearson r between per-cell detector AUC and mean dependence = **-0.2217**.
- **B_santos_to_rm, dns COMPROMISED:** across 85 conditions, Pearson r between per-cell detector AUC and mean dependence = **-0.7323**.
- **B_santos_to_rm, dns NOT compromised:** across 100 conditions, Pearson r between per-cell detector AUC and mean dependence = **-0.7259**.

**Verdict: the correlation here is NEGATIVE, which is the opposite sign to Part 14's, and the two are not measuring the same thing.** Part 14 swept one attacker objective and watched gate AUC and dependence fall TOGETHER along that axis (r = +0.9578 over six levels). Part 29 correlates across heterogeneous conditions at fixed attacker strength, and finds that the conditions with the HIGHEST measured dependence are the ones the detector scores LOWEST. Both readings are consistent with L8's underlying claim - that detection and correction are functions of one quantity - but the sign above must not be quoted as reproducing Part 14's.

The negative sign is close to mechanical, and worth stating because it sharpens [[L5]] rather than contradicting it. The suspicion score is agreement left UNEXPLAINED by the estimated dependence (`prismflow/statistics/suspicion.py`: `excess = agreement - expected` where `expected` rises with the estimated matrix). An attack that successfully manufactures dependence therefore raises `expected`, shrinks `excess`, and lowers its own suspicion score. Succeeding at collusion is itself what buys cover from a detector watching for collusion. Part 29 does not establish this mechanism - it measures the correlation, not the causal path - so it is offered as the likely reading, not a finding.

## 11. Coordination effect (beta)

`beta` is the weight on the chorus objective's agreement term, `sum_v log b_v[target] - beta * sum_{i,j} ||b_i - b_j||^2` (`prismflow/attacks/chorus.py`, `chorus_objective`). At `beta=0` that term is off and the attacker only maximises the target's likelihood; raising it pays the attacker to make the compromised views AGREE while doing so.

Every number below is a **paired within-seed difference** on one subset at `chorus k=2 eps=1.0`: the difference is formed seed by seed and only then averaged, so a pair whose seeds disagree in sign cannot read as `no effect`. The `same sign` column counts the seeds agreeing with the sign of the mean. A seed whose difference is **exactly 0.0** agrees with neither sign, so it is excluded from that count and disclosed in the cell as `(n exactly 0)`: a `1/5 (4 exactly 0)` is four seeds that did not move, NOT four seeds contradicting the mean. 36 of the 168 rows in this section are in that position. Read a low count WITHOUT a zero disclosure as a genuine sign split. **Nothing is pooled** across pairs, across the `dns` split or across the two directions.

**The gate on these rows, and what it is worth.** Two assertions run over every paired-difference row in this section before this file is written; either one printing an offending row aborts the write.

1. `check_sign_consistency`: if `|mean| > 2 * std` (population std) the seeds must be unanimous. **At n=5 this cannot fail, and is reported here as an invariant rather than as a check that passed.** The smallest population std a 5-seed vector can have while one seed disagrees is reached by putting that seed at 0 and the other four at 1.25 the mean, which gives `|mean|/std` exactly 2.0; every other non-unanimous arrangement is wider and scores lower. 2.0 is thus the attained supremum, so a strict `>` against it is a tautology at this n. It becomes load-bearing only at n>5. Measured headroom: the largest `|mean|/std` among the non-unanimous rows in this section is **1.6036**, against a bar of 2 that no 5-seed row can reach.

2. `check_wiring`: every row's printed `mean +/- std`, its `same sign` count and its `agree + exactly-0 + opposite` partition must all recompute from that row's own per-seed difference vector. This one CAN fail - it is what would catch a column read off the wrong cell or a mean and a count taken over different seed sets - and it is the assertion to trust.

The last column pair of the first four tables is a consistency check, not an effect: `run_ait_attack.py:501` passes `beta=beta if kind == "chorus" else 0.0`, so `pgd` and `chorus beta=0.0` get an identical config and differ only in which runner is called. `chorus beta 0.0 - pgd` should therefore sit at ~0 wherever the two implementations agree, and it says nothing about coordination.
